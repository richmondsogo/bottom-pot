# Bottom Pot Job Source Lifecycle Catalog

This document is the authoritative source-of-truth inventory and lifecycle ledger for every job board, Applicant Tracking System (ATS), remote-job feed, and other job source considered or integrated in Bottom Pot.

---

## 1. Purpose, Selection Principles & Evaluation Standard

Bottom Pot optimizes for **genuinely eligible, fresh technical jobs** that developers and technology professionals living in **Nigeria and elsewhere in Africa** can apply for (covering internship, junior, entry-level, and experienced roles), **not provider count**.

### Mandatory Evaluation Rules
1. **Optimize for genuinely eligible jobs, not provider count**: Do not prioritize or implement a source solely because it is popular, has high raw posting volume, offers a convenient API, is technically easy to scrape/integrate, or is consumed by other aggregators.
2. **Mandate geographically global source discovery**: Source discovery must be **geographically global**, not limited to Nigerian boards, US boards, or countries already represented in the codebase. Actively explore niche and regional technology job boards, specialist communities, remote-work aggregators, and employer networks across all regions (examples include Australia, Russia, Thailand, Singapore, Latin America, Europe, Africa, and other underrepresented markets) as an ongoing discovery responsibility—never a one-off list. Record candidates in this catalog **only** with concrete evidence and an explicit lifecycle state, not as a large speculative list.
3. **Strictly separate Source Geography, Job Geography, and Applicant Eligibility**:
   - **Source geography**: Where the job board or aggregator is based.
   - **Job geography**: Where the employer expects the role to be performed or where the role is located.
   - **Applicant eligibility**: Which countries applicants may reside in, work from, or hold work authorization for.
   - Never treat a board's country, an employer's headquarters, a job's location, or a generic `remote` / `is_remote=true` label as proof of applicant eligibility (e.g., a Thailand-based board can publish a role open to Nigerians; a US-based board can publish a remote role restricted to US residents). Evaluate actual job-level eligibility—especially for Nigerian and African applicants while including globally accessible roles—and classify eligibility as:
     - `Eligible`: explicit evidence permits applications from Nigeria or the relevant applicant location.
     - `Restricted`: explicit country, region, work-authorization, or hiring restrictions exclude the applicant.
     - `Unverified`: remote status exists, but applicant eligibility is unclear or contradictory.
   - Retain the supporting evidence behind each classification.
4. **Distinguish source categories & prefer direct employer career pages**:
   - Categories: `Employer ATS / career board`, `Regional technology job board`, `International remote-only board`, `Specialized programming or industry job board`, `General job aggregator`, `Talent marketplace or recruiting network`, `Professional community or job-posting feed`.
   - Prefer collecting original employer career-page URLs and monitoring employers directly when that offers better freshness, description quality, and deduplication. A source may be useful for employer discovery even when direct listing ingestion is legally or technically unsuitable.
5. **Before implementation, establish & respect permission gates**: verify public access & authentication, official API/feed documentation, explicit data reuse/redistribution rights, attribution & original application-link requirements, description completeness, stable identity, pagination & empty-feed semantics, expiration/closure signals, HTTP limits & conditional requests, geographic/work-authorization restrictions, relevant technical/early-career coverage, incremental value, duplicate coverage, and maintenance cost. Keep sources with unclear redistribution rights as `Discovery-only` or `Permission pending` — **public HTTP accessibility (`200 OK` without auth) is not permission to republish**.
6. **One provider at a time with bounded evidence**: Investigate, rank, and implement candidates one source at a time with bounded evidence before writing production code.
7. **Mandatory rejected-provider cleanup**: When a source is `Rejected` (`Unsuitable`) or `Retired`, audit the full repository and remove all active configuration, URL parsing, regexes, canonical URL builders, normalizers, enrichers, routers, adapters, frontend inventories, tests, and dependencies—retaining only justified shared code, historical investigation records (`docs/steps/`), backward-compatibility migration tables (`HISTORICAL_FULL_INVENTORIES`), and operational SQLite data (`data/cache.sqlite`). Never delete historical step evidence merely to make a repository search return zero matches. Keep this catalog synchronized after every investigation, approval, implementation, rejection, or retirement.

### Lifecycle States

| State | Meaning |
|---|---|
| `Discovered` | Candidate identified; not yet formally evaluated. |
| `Investigating` | Bounded empirical & documentation audit in progress. |
| `Discovery-only` | Direct listing ingestion/redistribution is not cleared; usable at most for discovering original employer career-page URLs (if robots/terms allow). |
| `Permission pending` | Technical/audience evaluation incomplete or explicit data reuse/redistribution permission has not been verified/granted; blocked from ingestion implementation. |
| `Approved` | Passed technical, audience-value, and permission evaluation; queued for dedicated bounded implementation. |
| `Implemented` | Active in production discovery/monitoring with full tests, fixtures, and safeguards. |
| `Constrained` | Active (or scoped to enrichment/search only) with documented technical, geographic, or coverage constraints. |
| `Rejected` | Evaluated as `Unsuitable` (or unclear permission); active integration code removed. |
| `Retired` | Previously configured/supported, now removed from active discovery/monitoring. |

## 3. Documented Exceptions for Retained References

Per the repository normalization policy, active provider registrations for rejected/retired sources must be removed, while existing shared or historical migration artifacts are preserved only with explicit justification:

1. **`frontend/src/lib/platformMigration.ts` (`HISTORICAL_FULL_INVENTORIES`)**: Retains historical platform IDs (`'breezy'`, `'polywork'`, `'rippling'`, `'pinpointhq'`) **strictly** so existing users upgrading from Step 27–49 `localStorage` state have their `"all platforms"` selections migrated cleanly to the active 20-platform set (and rejected IDs stripped from custom subsets).
2. **`src/project_files/url_normalizer.py` (`ngcareers` rule)**: Retains URL normalization for historical URLs without performing any active search or scraping.
3. **Operational database (`data/cache.sqlite`, `serper_cache`)**: Historical rows referencing rejected or retired providers are **never** deleted or migrated without separate authorization and an explicit migration plan.
4. **Historical step documents (`docs/steps/*`)**: Preserved intact as immutable engineering audit records, annotated where superseded (e.g., [Step 48](steps/48-personio-monitoring-investigation.md) annotating that `breezy` was subsequently rejected in [Step 50](steps/50-breezy-monitoring-investigation.md)).
